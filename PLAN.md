# PLAN — Undaunted Normandy веб-бот

## Цель и контекст

Пользователь играет в Undaunted: Normandy соло — сам за одну сторону,
вторая сторона разыгрывается по правилам простого соло-бота (см.
`bot_script.txt`). Бот — это не сценарий партии, а **дерево решений**:
для каждого типа юнита (стрелок, разведчик, пулемётчик, снайпер,
миномёт, командиры) есть приоритетный список действий и правила выбора
цели. Веб-приложение должно проводить игрока по этому дереву во время
игры: он выбирает юнита, чья карта выпала, отвечает на вопросы
да/нет/выбор ("может захватить?", "какая цель приоритетнее?"), а
приложение говорит, что делать.

## Решения по развилкам

- 2026-09-04: стек — Vite + React + TypeScript, без бэкенда (чистый
  фронтенд, статический деплой).
- 2026-09-04: git инициализирован (2 коммита сделаны). Push пока не
  сделан — ждём, пока пользователь создаст пустой репозиторий на
  GitHub и пришлёт URL (см. `HOSTING.md`).
- 2026-09-04: глубина модели — **только вопросы плюс калькуляторы**.
  Бот не хранит состояние стола (юнитов, координаты) и не считает
  расстояния сам за игрока, НО там, где в правилах есть формула
  сравнения чисел (ценность ключевой точки, выбор цели атаки, выбор
  квадрата миномёта) — игрок вводит числа (ПО/защиту/расстояние/
  количество), а бот сам применяет формулу и называет результат.
  Причина: игроку неудобно и легко ошибиться, сравнивая вручную
  несколько целей/точек в уме за столом. См. `src/components/
  KeyPointCalculator.tsx`, `TargetCalculator.tsx`, `MortarCalculator.tsx`.
- 2026-09-04: карта, которая разыгрывается на шаге раунда, выбирается
  игроком вручную из списка юнитов (карта тянется физически на столе,
  инициатива/порядок разыгрывания бот не автоматизирует в v1).
- 2026-09-04: оформление — военно-полевая тема (хаки/оливковый),
  ручной переключатель светлая/тёмная (сохраняется в localStorage,
  игнорирует системную тему после первого переключения). Обоснование
  пользователя: стиль должен соответствовать игре, но без потери
  читаемости — проверено на контраст в обеих темах.
- 2026-09-05: по итогам первой обкатки уточнено, что числа защиты в
  скрипте бота (4-6, 4-7/8-9/10, ≤8, 9+) означают **итоговую защиту с
  учётом расстояния**, а не базовую. Причина: решение «атаковать или
  нет» должно отражать реальный шанс попасть.
- 2026-09-05: перед деревом каждого боевого юнита стоит гейт «жетон на
  поле?», а перед шагами воодушевления — гейт «есть ли в зоне
  розыгрыша сыгранная карта нужного отряда». Оба проверяются вопросом
  игроку, состояние стола по-прежнему не хранится.
- 2026-09-05: Node поставлен портативно (распакованный zip в
  `~/.local/node`, в системный PATH не прописан) — по просьбе не
  засорять машину установщиком. Сборка и типы теперь проверяются
  локально; инструкция — `HOSTING.md`, раздел 0.
- 2026-09-05: тексты приложения следуют русской локализации коробки, а
  не `bot_script.txt` (любительский перевод): «Командир взвода»,
  «Командир отделения», «Наблюдать». Причина: игрок сверяет экран с
  картой в руке, названия должны совпадать буквально.
- 2026-09-05: пополнение (`OPEN_QUESTIONS.md` п. 13) получило правило
  выбора юнита — переиспользует существующий приоритет цели атаки, а
  не вводит отдельный список. Заодно вскрылся и починен смежный баг:
  `generalRule`/`reinforceRule` были в `CommonData` с первой версии
  схемы, но не входили в `memos` и потому никогда не рендерились —
  перенесены в `memos`.
- 2026-09-05: добавлена реакция на эндшпиль (`OPEN_QUESTIONS.md` п.
  12) — единственное решение в этом проекте, которого нет в
  `bot_script.txt` вообще ни в каком виде (это не конвертация, а новая
  механика по запросу). Реализована как обёртка дерева в коде
  (`getUnitTree`), а не правка JSON: обе ветки нового вопроса ссылаются
  на один и тот же исходный объект дерева, так что скрипт юнита
  физически не дублируется и не может разойтись при будущих правках.
- 2026-09-05: чистая логика калькуляторов вынесена из React-компонентов
  в `src/logic/` — компоненты остались тонкой обёрткой над формулами.
  Причина: формулы §4-6 и §11 — самое дорогое место для ошибки, их
  нужно проверять тестами, а не глазами. Тесты — `npm test` (vitest).
- 2026-09-05: выбор маршрута (`OPEN_QUESTIONS.md` п. 11) решён без
  хранения состояния поля — правило «кратчайший путь, обход только
  бесплатный» сформулировано как памятка игроку, а не расчёт бота.
  Заодно `memo` в `types.ts` расширен до `string | string[]`: одному
  узлу-действию иногда нужно нести сразу и формулу (ценность точки/
  выбор цели), и это новое правило маршрута.

## Что подтверждено

- Источник правил — `bot_script.txt` в корне проекта (полный текст
  правил соло-бота v1.0, разделы 1-14).
- Правила состоят из: общего алгоритма "первое доступное действие
  сверху вниз по скрипту юнита" + общих правил выбора цели (3 уровня
  приоритета + исключение "разница защиты ≥2") + отдельного скрипта
  действий на каждый тип юнита + отдельных мини-скриптов для командиров
  (сержант/зам.командира/командир).

## Структура правил из bot_script.txt (для конвертации в JSON)

- Общие правила (не привязаны к юниту):
  - Главное правило ИИ: первое доступное действие сверху вниз (§3)
  - Выбор цели, 3 уровня приоритета + список приоритетов по 2 сценариям
    цели ("Ключевые точки" / "Подавление") (§4)
  - Исключение по разнице защиты ≥2 (§5)
  - Формула ценности ключевой точки: ПО − расстояние, штрафы за контроль
    игроком (§6, "Как выбрать ключевую точку")
  - Правило §13: если у карты юнита нет нужного действия — пропустить
    шаг скрипта, но не пропускать саму карту целиком
  - Правило §14: пополнение — только если нет более важного действия
- Юниты со своим скриптом действий:
  - Стрелок — 2 варианта скрипта в зависимости от общей цели ИИ
    (Ключевые точки §6 / Подавление §7)
  - Разведчик (§8)
  - Пулемётчик (§9, с таблицей защита→действие)
  - Снайпер (§10, приоритет цели: офицер → пулемётчик/миномёт → стрелок
    → разведчик)
  - Миномёт (§11, обстрел квадратов, выбор квадрата)
  - Сержант / Заместитель командира / Командир (§12, отдельные
    мини-скрипты воодушевления/пополнения)
