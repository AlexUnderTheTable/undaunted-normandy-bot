# Открытые вопросы по конвертации bot_script.txt в JSON

Формат: описываю неоднозначность, предлагаю свою интерпретацию.
Оставляйте комментарии прямо под пунктом (строкой с `>`) — на следующем
шаге учту.

## 1. Стрелок, цель "Подавление" — шаги 4-5 (§7 bot_script.txt) — РЕШЕНО

Принята версия из комментария — чёткое дерево:

- Есть цель с защитой ≤8 → Атаковать.
- Лучшая цель имеет защиту 9+, но к ней можно приблизиться → Переместиться к ней.
- Иначе → Переместиться к предпочтительной цели атаки.
- Ничего из этого невозможно → Затаиться.

Применено в `src/data/shooter.json` (`trees.suppression`).

## 2. Как определяется "цель ИИ" (Ключевые точки / Подавление) — РЕШЕНО

Цель ИИ — глобальная настройка сценария (`aiGoal`), выбирается один раз
перед партией, не меняется по ходу игры. Влияет на:

- какую ветку скрипта использует Стрелок (`trees.keyPoints` /
  `trees.suppression` в `shooter.json`);
- общий приоритет цели атаки для всех юнитов (memo `"targetSelection"`
  в дереве → резолвится в `targetSelection_keyPoints` или
  `targetSelection_suppression` из `common.json` в зависимости от
  текущего `aiGoal`).

Детали механизма — см. `src/data/SCHEMA.md`.

## 3. Как игрок выбирает aiGoal перед партией? — РЕШЕНО

Подтверждено: простой переключатель в UI настроек ("Ключевые точки" /
"Подавление"), игрок ставит его сам по сценарию — сценарии на очки
победы (контроль зон) → "Ключевые точки", сценарии на уничтожение
отрядов → "Подавление". Бот это не вычисляет, только хранит выбор.

## 4. Пополнение у командиров: порядок §12 vs общее правило §14 — РЕШЕНО

§14 говорит в общем: "Командиры пополняют, если нет более важного
действия" (пополнение — низкий приоритет, самое последнее).

Но §12 для Сержанта прямо ставит "1. Пополнить, 2. Приказать" — то есть
пополнение как ПЕРВЫЙ шаг скрипта, выше приказа. Для Командира скрипт
чередует "воодушевить/пополнить/воодушевить/пополнить".

Сейчас в JSON (`sergeant.json`, `lieutenant.json`, `commander.json`) я
следую буквальному порядку из §12 для каждого юнита (считаю, что
конкретный скрипт юнита важнее общей упрощающей ремарки §14).

У `commander.json` в конце два разных смысла "Пополнить" из §12 (шаг 2
и шаг 4) схлопнулись в один вопрос — при отсутствии состояния стола
второй вопрос ничем не отличается от первого, поэтому финальный узел
дерева сейчас — просто действие по умолчанию, а не повторный вопрос.

Подтверждено: при конфликте §12 и §14 применяется конкретный скрипт
юнита из §12; второе "Пополнить" в `commander.json` остаётся финальным
действием по умолчанию, отдельным вопросом становиться не обязано.

## 5. Штраф для точки: под контролем игрока, но дойти некому — РЕШЕНО

В §6 bot_script.txt три градации штрафа для ключевой точки:

> −2, если её контролирует игрок и на ней стоит его юнит;
> −1, если игрок контролирует её и его юнит может до неё добраться;
> −0.5, если игрок только разведал её.

Не описан случай: точка под контролем игрока, юнита на ней нет, и
дойти туда в этот ход тоже некому (то есть не подходит ни под −2
"стоит юнит", ни под −1 "может дойти", и это не просто "разведана" —
она реально под контролем). В `bot_script.txt` такой случай не назван.

Варианты:
- **0 (нет штрафа)** — раз в этот ход отбить точку игрок не может, для
  ИИ она сейчас так же привлекательна, как нейтральная.
- **−0.5** — приравнять к "только разведана" (игрок присутствует на
  поле, но не рядом с этой точкой прямо сейчас).
- **−1** — приравнять к "может дойти" (сам факт контроля важнее
  сиюминутной досягаемости юнита).

Принято: штраф **0**. Правило-интерпретация для спецификации: если
ключевая точка контролируется игроком, но на ней нет его юнита и ни
один его юнит не может достичь её в рамках текущего перемещения —
применяется штраф 0 (точка временно так же привлекательна, как
неконтролируемая). Применено в `src/components/KeyPointCalculator.tsx`.
